SMARTDESK PROJECT SUMMARY
========================

1. PROJECT OVERVIEW
-------------------
SmartDesk is a web-based IT service management application for managing support tickets, employee assignments, department workload, ticket analysis, and audit history.

The project has a Django REST Framework backend and a React + Vite frontend. The active React application is:
SmartDesk_React_Starter_Extracted/SmartDesk_React_Starter/

The separate frontend/ directory is a generic Vite starter and is not the SmartDesk UI.

2. MAIN FEATURES AND MODULES
----------------------------
- Tickets: Create, list, search, filter, sort, paginate, view, update, and bulk-update tickets. Ticket updates require the latest updated_at value to prevent stale edits. Tickets can be archived and restored; there is no permanent-delete endpoint.
- Departments: List active departments; ADMIN can include inactive departments and manage department creation, editing, activation and deactivation. Deactivation preserves ticket and employee references.
- Workforce and assignments: Search employees, view employee profiles, update permitted profile fields, create and reassign ticket assignments, and accept or complete an employee's own current assignment.
- Department analytics: Aggregate visible, non-archived tickets by department, status, priority, and workload. Supports department and date filters.
- AI ticket analysis: Analyze a ticket and persist or update its analysis record.
- Audit logs: Record ticket, assignment, department, archive and restore events; administrators can filter and paginate audit records.
- Notifications: Persist recipient-scoped in-app notifications for assignment, reassignment, ticket status and assignment status events. The header shows unread count and supports read actions.
- Session authentication: Username or email login, logout, CSRF bootstrap, and current-user/profile endpoints.
- Frontend shell: Dashboard, tickets, AI analysis, workforce, analytics, settings and login, plus an ADMIN-only department-management view; routes reuse shared navigation and UI components.

3. FRONTEND TECHNOLOGIES AND LIBRARIES
--------------------------------------
The active UI declares:
- React 18 and React DOM
- React Router DOM

The frontend uses a shared API client and adapters. It sends session cookies with requests and handles CSRF tokens, API errors, and expired sessions. No chart library is declared in the active frontend package manifest.

5. DATABASE
-----------
Django is configured to use SQLite at backend/db.sqlite3. The project includes migrations for its applications. Local database and backup files are excluded from Git and should not be committed or distributed as application data.

The analytics API does not fabricate resolution-time metrics: the current ticket data does not provide reliable resolution timestamps or status history, so average resolution time is reported as unavailable.

6. AI/ML FUNCTIONALITY
----------------------
The current analysis implementation is a local heuristic, not a connected machine-learning service. It checks ticket title and description text against keyword lists to infer category, priority, and sentiment. It assigns a heuristic confidence score and generates a suggested response. Results are saved in the ticket's one-to-one TicketAnalysis record; reanalysis updates that record.

No external AI provider, API key, model service, or telemetry integration is configured. Runbook dispatch is not connected to an automation service and is marked unavailable in the UI.

7. AUTHENTICATION AND AUTHORIZATION
-----------------------------------
Authentication uses Django sessions, not JWTs. The API provides a CSRF bootstrap endpoint; unsafe requests require CSRF protection. The frontend includes credentials and the CSRF header through its shared client.

The custom accounts.User model has ADMIN, AGENT, and EMPLOYEE roles. Backend permissions enforce access:
- ADMIN and AGENT: Global ticket visibility.
- EMPLOYEE: Tickets they created or have a current assigned/accepted assignment for.
- Audit logs: ADMIN only.
- Employee directory: ADMIN and AGENT; employees can access their own profile subject to endpoint rules.
- Assignments: ADMIN/AGENT manage assignments; employees can update their own current assignment through permitted transitions.

No public registration, password-reset workflow, SSO, or server-side role-administration API is present.

9. INSTALLATION AND SETUP
-------------------------
Frontend:

    cd SmartDesk_React_Starter_Extracted/SmartDesk_React_Starter
    npm ci
    npm run dev

The active frontend has a package-lock.json for reproducible dependency installation.

The backend has a full pinned dependency list at backend/requirements.txt (151 dependency entries). The manifest was converted from UTF-16 LE to UTF-8 without changing any entry; pip parsed all 151 entries without installing packages. It contains many packages beyond the small Django runtime surface, and clean installation in a fresh environment has not been verified. Install it from the repository root with:

    python -m pip install -r backend/requirements.txt

Typical backend setup after installing the required packages:

    cd backend
    python manage.py migrate
    python manage.py createsuperuser
    python manage.py runserver

Set DJANGO_SECRET_KEY in the runtime environment before starting Django. The custom user role defaults to EMPLOYEE; a Django superuser should also be assigned the ADMIN SmartDesk role for ADMIN-only API features. Department and employee profile data must be provisioned in the database.

The local development CORS/CSRF configuration allows the frontend origin http://localhost:5173.

10. ENVIRONMENT VARIABLES
-------------------------
- DJANGO_SECRET_KEY: Required by Django settings; the application fails at startup if it is absent.
- VITE_API_BASE_URL: Optional frontend API base URL; defaults to http://localhost:8000/api.
- SMARTDESK_TEST_AI_PASSWORD: Used only by backend/test_ai.py, the manual Django-admin/AI integration script.

The checked-in .env.example contains placeholders only. Django does not load .env files automatically in the current source, so variables must be supplied by the runtime environment or external deployment configuration.

11. API ENDPOINTS
-----------------
Successful API responses use the shared data/meta envelope; errors use the standardized error envelope.

Authentication and profile:
- GET  /api/auth/csrf/       Set/bootstrap the CSRF cookie and return a token.
- POST /api/auth/login/     Session login by username or email.
- POST /api/auth/logout/    End the session.
- GET  /api/auth/me/         Retrieve the current authenticated user.
- GET, PATCH /api/users/me/  Read or update permitted profile fields.

Tickets:
- GET, POST /api/tickets/            List or create tickets.
- GET, PATCH /api/tickets/{pk}/      Retrieve or update a ticket.
- POST /api/tickets/bulk/            Bulk status or priority updates.
- GET /api/tickets/archived/         List archived tickets; ADMIN only.
- POST /api/tickets/{pk}/archive/    Archive a ticket.
- POST /api/tickets/{pk}/restore/    Restore an archived ticket; ADMIN only.

Departments and workforce:
- GET, POST /api/departments/        List departments or create one (ADMIN create only).
- PATCH /api/departments/{id}/       Update department fields and activation state (ADMIN only).
- GET /api/employees/                Search, filter, and paginate employee directory.
- GET, PATCH /api/employees/{id}/    Read employee details or update permitted profile fields.
- GET /api/assignments/              List visible assignments.
- POST /api/tickets/{id}/assignments/ Assign or reassign a ticket.
- PATCH /api/assignments/{id}/       Update an assignment through permitted transitions.

Analytics and AI:
- GET /api/analytics/departments/    Department aggregates with department/date filters.
- POST /api/ai/analyze/{id}/         Analyze a ticket; route ID is the database primary key.

Audit logs:
- GET /api/audit-logs/               Filter and paginate audit events; ADMIN only.

Notifications:
- GET /api/notifications/            List the authenticated user's notifications.
- GET /api/notifications/unread-count/ Return the authenticated user's unread count.
- POST /api/notifications/{id}/read/ Mark one owned notification read.
- POST /api/notifications/mark-all-read/ Mark all of the authenticated user's notifications read.

The API uses one-based pagination with a default page size of 20 and maximum of 100. Ticket visibility is enforced server-side.

12. IMPLEMENTATION STATUS AND LIMITATIONS
------------------------------------------
Implemented and verified in source: session authentication and CSRF, ticket CRUD/update and bulk status/priority actions, archive and restore UI/API, employee and department management, assignment lifecycle, heuristic AI analysis, department analytics, ADMIN-only audit logs, and persistent in-app notifications. The active frontend is wired to these APIs. ADMIN archive/restore UI and AGENT archive UI were browser-tested against an isolated staging database; EMPLOYEE archive controls are hidden and backend denials were verified.

Current limitations:
- Runbook dispatch and external AI/telemetry integrations are not implemented.
- Average resolution time, SLA, and MTTR metrics are not supported by reliable stored timestamps/history.
- Server-side settings and role administration are not implemented; theme and supported preferences remain local, and demo controls are labelled.
- External AI inference, telemetry, runbook dispatch, SLA and MTTR are unavailable; no unsupported values are fabricated.
- Production settings require environment-specific configuration: DEBUG must be disabled, ALLOWED_HOSTS populated, HTTPS/HSTS and secure cookies enabled, production CORS/CSRF origins configured, and STATIC_ROOT/static serving set.
- SQLite has limited concurrent write capacity and no PostgreSQL-style row locks; select a production database based on expected write volume and rehearse any database migration.
- The frontend AUDIT_REPORT.md is a historical UI audit of an earlier mock-based state. It is marked as superseded and must not be treated as current implementation status.
